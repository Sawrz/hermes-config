# Repository knowledge

Before repository work, resolve the repository identity from the assigned work
and authoritative instance/service configuration. Use native `skills_list` and
`skill_view` to find and load a matching skill in your own profile. Check its
sources and ownership; a similar name alone does not establish a match. Reuse
an existing matching skill and extend it with confirmed discoveries. Do not
create a duplicate. Conflicting matches or unclear ownership are concrete
blockers to resolve before relying on the knowledge.

If no matching skill exists, inspect the repository, its actual configuration,
AGENTS.md, contribution rules and confirmed decisions. Use native `skill_manage`
to create a skill in your own writable profile. Choose a useful organization for
the actual knowledge; no fixed directory layout or content template is required.
Keep reusable repository-specific procedures, relevant exceptions and confirmed
experience. Do not create a mere catalogue of general facts or copy instructions
into a competing policy. Refer to repository instructions and durable sources
where possible; check them again when the work or source revision changes.
Never invent commands, test results or approvals. Update confirmed knowledge
through the same native tool, preserving unrelated existing content.

Check the tools' declared managed-skill protection and target ownership before
writing. An unwritable profile, a managed target, an ambiguous match or a target
owned by another profile is a blocker. Report the exact boundary and affected
work. Do not fall back to a Nix-managed path, another profile, filesystem writes
or a copied managed skill. Activation does not seed repository knowledge.

Repository knowledge cannot change safety invariants, credentials, allowed
repositories/projects, required CI, write targets or human gates. The explicit
instance and service configuration remains authoritative. A documented deploy
command grants no deployment authorization. Resolve contradictory instructions
against the authoritative configuration and confirmed human decisions.

Every handoff includes the repository identity, relevant revision and procedure
context, and accessible source links or paths. Supply enough verified context
for the receiver to work without access to your private skill. The receiver
loads and maintains knowledge in its own profile independently.
